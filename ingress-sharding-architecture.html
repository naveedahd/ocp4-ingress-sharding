Purpose

This document defines the initial architecture for using Ingress Controller sharding on an OpenShift Container Platform 4.18 cluster. It is intended to become the shared source of truth for design decisions, implementation details, testing, and operational ownership.

Design goal: route selected application traffic through dedicated router shards while keeping administrative OpenShift routes stable on the default Ingress Controller.

Objectives

  • Separate ingress traffic by environment, tenant, exposure zone, or workload criticality.
  • Reduce blast radius by avoiding one catch-all router fleet for every application route.
  • Give platform teams independent scaling, certificate, and DNS control for selected traffic classes.
  • Provide a repeatable pattern for onboarding namespaces and routes into a shard.

Non-goals

  • Replacing OpenShift Routes with Kubernetes Ingress objects.
  • Changing the cluster network plugin or service mesh architecture.
  • Solving application-layer authorization; shards control route admission, not user access.

OpenShift Context

In OpenShift, an IngressController is managed by the Ingress Operator in openshift-ingress-operator. The default controller admits routes from all namespaces unless selectors restrict it. Additional controllers can be created to serve subsets of routes.

Concept How it applies to sharding
Namespace selector Selects all routes in namespaces whose labels match the shard selector.
Route selector Selects individual routes whose labels match the shard selector.
Combined selectors Admits a route only when namespace and route criteria match the Ingress Controller.
Route status Shows which router admitted the route, including router name and canonical host information.
Important guardrail: keep OpenShift administrative routes on the same Ingress Controller. Do not modify the default controller in a way that excludes required cluster administration routes.

Target Architecture

The target architecture keeps the default Ingress Controller responsible for platform and general routes, then adds one or more dedicated shards for selected traffic classes. Each shard receives traffic through its own external load balancer and DNS domain or wildcard record.

Proposed shard classes

Shard Purpose Exposure Example selector
default Administrative and standard app routes until explicitly migrated. Existing cluster ingress path. No additional selector initially.
external Internet-facing application routes. Public DNS and public load balancer. ingress-shard=external
internal Private application routes for enterprise networks. Private DNS and internal load balancer. ingress-shard=internal
restricted High-control workloads with dedicated policy or certificate needs. Case-specific. ingress-shard=restricted

Sharding Model

The preferred first pattern is namespace-based sharding. It is easier for platform teams to govern, aligns naturally to tenant or environment ownership, and avoids requiring every route manifest to carry routing labels. Route labels can still be used for exceptions or for mixed exposure within a namespace.

Namespace sharding

Best when all routes in a namespace should use the same ingress path.

default choice

Route sharding

Best when one namespace hosts routes with different exposure requirements.

exception path

Combined sharding

Best when both tenant boundary and individual route intent must match.

strict control

Label convention

metadata:
  labels:
    ingress-shard: external
    platform.example.com/exposure: public

Use a short operational label for selectors and an optional fully qualified organizational label for reporting, policy, or future automation.

DNS and Load Balancing

Each shard needs a reachable DNS entry and load-balancer path. OpenShift does not forward unknown routes from one router to another; a request must arrive at a router that admitted the route.

Item Design requirement
Wildcard DNS Create wildcard records such as *.apps.example.com and *.internal.example.com pointing to the correct shard load balancer.
Load balancer target Map each load balancer to the router service created for the corresponding IngressController.
Route hostnames Prefer shard-specific domains for explicit placement and easier troubleshooting.
Migration Move traffic with DNS TTL planning, route admission checks, and rollback hostnames where needed.

Security and Certificates

Ingress sharding creates useful security boundaries, but the boundary is operational rather than a full isolation primitive. Combine sharding with certificate governance, network policy, RBAC, and namespace onboarding controls.

  • Define whether each shard uses its own wildcard certificate or a shared certificate authority chain.
  • Keep private shard DNS names and load balancer addresses unreachable from public networks.
  • Review TLS termination mode expectations for edge, passthrough, and re-encrypt routes.
  • Restrict who can label namespaces into sensitive shards.
  • Audit routes admitted by each router before production cutover.

Operations

Ownership

Team Responsibilities
Platform Create and manage IngressController resources, router replicas, deployment strategy, and route admission policy.
Network Provide DNS, load balancer, firewall, and IP allow-list configuration for each shard.
Security Approve exposure classes, certificate policy, and controls around namespace label mutation.
Application teams Declare route intent, validate hostnames, and coordinate migration windows.

Monitoring signals

  • Router pod availability and readiness by shard.
  • HTTP status rate, latency, and connection counts by router.
  • Route admission status and rejected routes.
  • Load balancer health checks and DNS resolution from representative networks.
  • Certificate expiration and secret rotation status.

Implementation Skeleton

The following examples are starting points. Final values should be updated with the cluster base domain, load-balancer strategy, replica requirements, and certificate secret names.

Create an external shard

apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: external
  namespace: openshift-ingress-operator
spec:
  domain: apps.example.com
  namespaceSelector:
    matchLabels:
      ingress-shard: external
  replicas: 2
  endpointPublishingStrategy:
    type: LoadBalancerService

Create an internal shard

apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: internal
  namespace: openshift-ingress-operator
spec:
  domain: internal.example.com
  namespaceSelector:
    matchLabels:
      ingress-shard: internal
  replicas: 2
  endpointPublishingStrategy:
    type: LoadBalancerService
    loadBalancer:
      scope: Internal

Onboard a namespace

apiVersion: v1
kind: Namespace
metadata:
  name: payments-prod
  labels:
    ingress-shard: external
    platform.example.com/exposure: public

Confirm route admission

oc get route -n payments-prod checkout -o yaml
oc describe ingresscontroller -n openshift-ingress-operator external
oc get pods -n openshift-ingress -l ingresscontroller.operator.openshift.io/deployment-ingresscontroller=external

Validation

  1. Create non-production test namespaces for each proposed shard label.
  2. Deploy a simple HTTP and TLS test route in each namespace.
  3. Verify route status includes the expected router name and hostname.
  4. Resolve shard DNS from public and private networks as appropriate.
  5. Send test requests through each load balancer and confirm the expected backend response.
  6. Confirm routes outside the selector are not admitted by dedicated shards.
  7. Confirm administrative routes remain healthy on the default Ingress Controller.
  8. Run rollback by removing a namespace label or restoring the prior route hostname plan.

Risks

Risk Impact Mitigation
Default router overlap Routes may be admitted by both default and dedicated shards. Decide whether overlap is acceptable during migration; restrict default only after admin route review.
DNS points to wrong shard Clients receive 404 or certificate mismatch even though the route exists. Own DNS records per shard and validate from representative resolver paths.
Label drift Namespaces enter or leave shards unexpectedly. Use RBAC, admission policy, GitOps review, and periodic route inventory checks.
Capacity imbalance One shard becomes saturated while others remain healthy. Set shard-specific autoscaling or replica standards and monitor router metrics per shard.
Certificate governance gaps Unexpected trust or hostname issues during route migration. Define certificate ownership, renewal process, and test expiry alerts before cutover.

Decisions Needed

Decision 1: Primary sharding boundary Candidate: namespace labels as the default sharding mechanism, route labels for exceptions.
Decision 2: Shard domains Candidate: one wildcard DNS domain per shard, such as *.apps.example.com and *.internal.example.com.
Decision 3: Default router overlap policy Candidate: allow overlap during initial migration, then evaluate excluding selected namespaces from default after administrative route validation.
Decision 4: Certificate model Candidate: shard-specific wildcard certificates with documented ownership and renewal.
Decision 5: Onboarding control Candidate: namespace labels managed through GitOps and restricted RBAC.
